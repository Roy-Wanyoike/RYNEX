# RYNEX Data module — append-only audit trail

Issue #20. A single, platform-wide audit trail that every RYNEX module
(Trust, Passport, Commerce, Finance, Fleet, ...) appends to, and admins can
query through the versioned gateway (`/api/v1/data`).

## Why append-only

An audit trail is evidence: once an action is recorded, the record itself must
be as trustworthy as the action was real. If rows could be edited or deleted,
the trail would prove nothing. Therefore:

- **No public write endpoint, by design.** The HTTP surface of this module is
  read-only. Clients can never create, change, or remove audit rows.
- **One write path, INSERT-only.** Rows are appended by server code via
  `recordAudit` -> `spWriteAudit`, a stored procedure that contains exactly one
  DML statement: an `INSERT`. There is no UPDATE/DELETE procedure anywhere.
- **Server-owned fields.** `logId` (GUID) and `createdAt` (`SYSUTCDATETIME`,
  UTC) are never taken from client input; `metadata` must be valid JSON
  (`ISJSON` check, `THROW 51001` otherwise) so the trail stays machine-queryable.
- **Fail loud on write, never break the flow.** `spWriteAudit` rejects malformed
  entries instead of writing them, while `recordAudit` treats any failure as
  non-fatal (logged via `console.error`) so auditing can never take down a
  business operation.
- Optional per-environment hardening (run manually once the app login is known):
  `DENY UPDATE, DELETE ON dbo.auditLog TO <app_login>;`

## Schema (`database/extensions/data.sql`)

Table `dbo.auditLog`:

| Column        | Type           | Notes                                            |
|---------------|----------------|--------------------------------------------------|
| `logId`       | `VARCHAR(50)`  | PK, GUID (36 chars) generated by `recordAudit`   |
| `actorUserId` | `VARCHAR(50)`  | NULL = system-originated action                  |
| `action`      | `VARCHAR(50)`  | what happened, e.g. `CAR_ADDED`                  |
| `entityType`  | `VARCHAR(30)`  | e.g. `USER`, `CAR`, `CART`, `PASSPORT`, `TX`     |
| `entityId`    | `VARCHAR(50)`  | NULL = action not tied to one entity             |
| `metadata`    | `NVARCHAR(MAX)`| optional JSON document, `ISJSON`-validated       |
| `createdAt`   | `DATETIME2`    | UTC, `DEFAULT SYSUTCDATETIME()`                  |

Indexes: `IX_auditLog_EntityType_EntityId (entityType, entityId)` for entity
lookups, `IX_auditLog_CreatedAt (createdAt)` for newest-first scans.

Stored procedures:

| Procedure            | Purpose                                                        |
|----------------------|----------------------------------------------------------------|
| `spWriteAudit`       | append one row (INSERT only; validates JSON, `THROW 51001/51002`) |
| `SpGetAuditByEntity` | all rows for one entity (`entityType` + optional `entityId`), newest first |
| `spGetRecentAudit`   | newest N rows, newest first; N clamped to 1..200 (default 50)  |

## HTTP API (admin only — `verifyToken` + `requireAdmin`)

| Route                                     | Description                                              |
|-------------------------------------------|----------------------------------------------------------|
| `GET /api/v1/data/audit?entityType=&entityId=` | audit rows of one entity, newest first. `400` when `entityType` is missing; `entityId` optional |
| `GET /api/v1/data/audit/recent?top=50`    | newest audit rows; `top` clamped to 1..200 (missing/invalid -> 50) |

Responses use the standard envelope `{ success, message, data? }`.

## How other modules adopt `recordAudit`

```ts
import { recordAudit } from '../Data/recordAudit'

await recordAudit(actorUserId, 'CAR_ADDED', 'CAR', carId, { model: car.model }) // fire-and-forget safe
```

Two rules for integrators: (1) call it **after** the business action has
committed (audit what actually happened, never what you hope will happen), and
(2) never branch business logic on its result — it is fire-and-forget by
contract. Standard actions are typed in `recordAudit.ts`
(`USER_REGISTERED`, `CAR_ADDED`, `CAR_SOFT_DELETED`, `CART_ITEM_ADDED`,
`PASSPORT_CREATED`, `PASSPORT_EVENT_ADDED`, `TX_STATUS_CHANGED`,
`BOOKING_STATUS_CHANGED`, `TRUST_RATED`) but any custom string is accepted.

## Retention policy

**PLACEHOLDER — to be decided.** The trail is currently retained indefinitely.
Candidate policy for a future PR: partition/prune by `createdAt` (e.g. keep
hot data 90 days, archive to cold storage 7 years) plus a legal-hold flag.
Append-only means retention jobs may only archive or drop *whole, aged-out
rows* — never rewrite them.

## Spec mapping

- **Evidence Vault (#39)** — `auditLog` is the immutable, timestamped evidence
  layer: every Trust/Passport/Finance artefact can reference trail rows as
  proof of what happened and when (UTC), with the actor recorded.
- **Evidence Vault (#48)** — hash-chained/notarised audit hardening builds on
  this table; its append-only guarantee and JSON metadata are the contract
  that future chaining will extend (e.g. row hashes over `logId + createdAt`).
- **Data Platform** — this module is the first platform-wide dataset: one
  schema, one write path, indexed for entity and time-series queries, consumed
  through a stable versioned gateway.
- **Analytics** — `metadata` (valid JSON, `NVARCHAR(MAX)`) plus `action` /
  `entityType` dimensions make the trail directly analysable (funnels, abuse
  detection, activity reports) via `SpGetAuditByEntity` / `spGetRecentAudit`
  today and warehouse exports later.
